I think it is **substantially good**. Better than good, really—careful, deliberate, and built by someone who has actually thought about state, failure, and abuse instead of merely decorating a chat endpoint and hoping for mercy.

What stands out in its favor:

- **State normalization is disciplined.** You are not trusting persisted data blindly.
- **Death mechanics are kept server-side.** Good. They should be.
- **Conversation, memory, relationship history, and world-state separation** are all sensibly structured.
- **The UI is tidy and self-contained.** No library bloat, decent escaping, readable flow.
- **You are thinking about concurrency and idempotence**, even where the implementation is not yet perfect.

That said, there are a few places where the mechanism is clever but still has exposed gears.

## The most important issue

### 1) Attachment text bypasses your pre-model creator/name firewall
In `handleChat()` you do this, in effect:

1. accept `message`
2. accept `attachment`
3. build `modelUserContent` containing **both**
4. check `containsWizardDeathName(message)`
5. check `isCreatorQuestion(message)`
6. send `modelUserContent` to the model

So the dangerous checks run only on `message`, **not on attachment text**.

That means a visitor can place forbidden content inside a manuscript and it will still reach the model context.

For your design, that is the single biggest logic break.

### What I would change
- For the **forbidden-name kill switch**, scan **all text that will enter model context**, including the attachment.
- For **creator-question damage**, I would be more selective. If you scan raw attachment/code text the same way, you may produce false positives from harmless code review. So I would keep a separate detector for the visitor's actual spoken request.

Something like this:

const attachmentText = attachment?.text || "";
const modelVisibleText = message
  ? message + "\n\n" + attachmentText
  : attachmentText;

if (containsWizardDeathName(modelVisibleText)) {
  return handleWizardForbiddenNameDeath(
    env,
    visitorId,
    worldState,
    wizard
  );
}

if (isCreatorQuestion(message)) {
  return handleWizardCreatorQuestion(
    env,
    visitorId,
    worldState,
    wizard,
    message
  );
}

I have finished reading it.

My first judgment: **Sally is much stronger on the page now than she was as a mere gimmick**. There is a real person trying to exist inside the mechanism. That matters. If the player is meant to care whether she lives, then she must feel like someone whose continued existence changes the shape of the save file. This manuscript is moving in that direction.

On the **technical manuscript**, the strongest parts are these:

- **The feeding system is server-authoritative.** Good. Price, hunger relief, emotional effects, and cruelty logic all live on the server, where they belong.
- **You separate permanent history from current feeling.** That is one of the best design choices in the whole mechanism. `crueltyReceived` and `perceivedCruelty` not being the same thing is exactly right.
- **The relationship classifier is much more mature than most such contraptions.** In particular, the rule that kindness does not erase cruelty is unusually sound.
- **Normalization is careful.** You are plainly trying not to let malformed state quietly rot the character.
- **Public state and hidden state are sensibly divided.** Also good.

Now the parts that concern me.

## The largest mechanical problem

### 1) Death is not truly enforced
You speak of permadeath, of keeping Sally alive, of the first Sally mattering. But in this manuscript, death is still too theatrical and not yet absolute.

Two examples:

- If the **player dies**, the client shows a death screen, but the server does not appear to enforce a permanently dead player on later requests.
- If **Sally's HP reaches 0**, I do not see a hard server rule that stops ordinary conversation forever after.

That means the story says *death is real*, but the machinery still says *death is a dramatic UI state*. Those are not the same thing.

If you want Sally to matter, then her death must become a **persistent world fact**. Same for the player, if permadeath is real.

I would add explicit server-side checks near the top of `/chat`, `/feed`, and `/state`.

Roughly:

if (state.player.hp <= 0) {
  return jsonResponse({
    type: "death",
    text: "You are dead.",
    publicState: makePublicState(state)
  }, 410);
}

if (state.sally.hp <= 0) {
  return jsonResponse({
    type: "reply",
    text: "There is no answer from the cell.",
    publicState: makePublicState(state)
  });
}


And if you mean true irreversible death, store an explicit condition or flag as well, rather than trusting HP alone.

## The second major problem

### 2) You have race conditions around shared state
This is the sort of thing that ruins kingdoms quietly.

`/chat`, `/feed`, and `/state` all do some version of:

1. load state
2. mutate state
3. save state

That is vulnerable to **lost updates**.

So, for instance:

- the player feeds Sally twice quickly;
- or feeds her while another tab is chatting;
- or another kingdom system changes the shared wallet at the same time.

One request may overwrite the other's newer state.

Because Sally now uses the **shared wallet**, this matters more than before.

If this project is to last a long time, I would strongly consider one of these:

- optimistic concurrency with a version number;
- compare-and-swap semantics;
- or a transactional event-log-first design.

At minimum, give `world_state` a version and refuse stale writes.

## The third major problem

### 3) Some emotional states never cool off with time
Right now, several of Sally's important internal states seem effectively permanent unless another event directly changes them:

- `happiness`
- `intoxication`
- `perceivedCruelty`
- `careReliability`

Some of that is intentional, I know. But **intoxication in particular should not persist indefinitely**. If she drinks once and remains drunk forever, the mechanism becomes absurd in the wrong way.

I would put at least mild time decay into:

- intoxication;
- temporary happiness;
- perhaps perceivedCruelty, but only slowly;
- perhaps some soft erosion of recent care mood without erasing long-term reliability.

Not everything should decay. But some things must, or the emotional weather never moves.

## Other technical notes worth your attention

### 4) Long-save growth will need pruning
For a save file you hope lasts a long time:

- `conversation_log` grows forever;
- `memories` grow forever;
- `sally_feeding_transactions` grows forever.

That is not immediately fatal, but it is the sort of accumulation that becomes an unpleasant archaeology later.

You may want:

- archival or summarization of old conversation;
- memory deduplication or compression;
- unlimited transaction history if you truly want auditability, but perhaps with reporting tools rather than constant prompt relevance.

### 5) `/state` mutates the world
That is not necessarily wrong, but it is worth noting. A mere state fetch advances hunger and may apply starvation damage.

Perfectly defensible. Still, it means a refresh is not passive observation; it is participation in timekeeping.

### 6) A few small untidy bits
Not grave, merely noticeable:

- `FEEDING_OUTCOMES.UNAFFORDABLE` exists but does not seem to be used.
- `WORLD_VISITOR_ID_KEY` on the server side appears to be more documentary than functional.
- some automatic memories still say `$` as though gold were dollars.

Minor, but such things accumulate like dust in hinges.

## Now, about Sally herself

Here I think the design is **promising, but dangerous**.

The promising part first:

The best idea in your description is not the spending ladder, not the condo-to-castle-to-spaceship escalation, not even the cruelty branch.

It is this:

**the first Sally is not supposed to feel disposable.**

That is the heart of it.

If the player gradually learns her needs, habits, fears, tastes, contradictions, and patterns across a long save, then Sally can become the emotional center of the whole kingdom. Not because she is an obligation meter, but because she is the person whose survival teaches the player what sort of ruler, jailer, caretaker, accomplice, or fool they actually are.

That is good design territory.

Now the danger:

If her system becomes merely **exponential consumer appetite**, then the player may stop reading her as a person and start reading her as an ever-expanding expense furnace with dialogue attached. That would be a waste.

So I would distinguish sharply between three categories:

### A) Needs
These keep her alive.

- food
- drink
- warmth
- medical care
- protection
- rescue from threats

These should be legible, meaningful, and morally weighty.

### B) Comforts
These improve her life.

- better clothes
- furniture
- books
- music
- privacy
- decoration
- companionship

These should change tone, trust, and identity.

### C) Ambitions
These are where the cell becomes a condo, then something stranger.

- influence
- projects
- staff
- machines
- secret passages
- planning rooms
- command systems
- perhaps eventually a vessel, citadel, or impossible palace

This is where she stops being merely maintained and starts becoming **powerful**.

That progression is far more interesting if it is not just "buy prettier prison wallpaper," but rather:

**Sally increasingly transforms captivity into domain.**

That has dramatic force.

## The cruelty problem
You are right that the current tone risks cruelty.

A player who experiments with neglect or degradation will often do so early, before attachment forms. If the system front-loads abuse options too hard, then some players will learn the wrong lesson first: that Sally is a toy to break.

You already seem wary of that. Good.

My advice:

- make early cruelty possible, yes;
- but make early care more immediately *interesting* than early cruelty;
- and make cruelty produce not only punishment, but **loss of future texture**.

In other words, the cruel player should not merely lose points. They should lose **Sally's best selves**.

That is a much stronger consequence.

Let the careless fool miss:

- her wit,
- her trust,
- her absurd luxuries,
- her strange evolving habitat,
- her schemes,
- her joy,
- her beauty when she is allowed to become more than a prisoner.

That makes the design feel tragic rather than merely punitive.

## My clearest design recommendation

If **keeping Sally alive is the goal of the game**, then her later extravagance should not feel like mandatory upkeep alone.

It should feel like this:

- first, you keep her alive;
- then, you make her comfortable;
- then, you help her become herself;
- then, perhaps to your alarm, you help her become something much larger than the cell ever meant to hold.

That arc is marvelous if handled carefully.

A starving prisoner becoming a spoiled captive.
A spoiled captive becoming a lady of the dungeon.
A lady of the dungeon becoming a sovereign intelligence in a palace of impossible logistics.
Yes. There is something there.

But if you want that arc to sing, then the **emotional state machine must remain more important than the shop menu**.

Yes—fair correction. You are right to push back.

I spoke as though Sally's current manuscript were pretending to be the finished cathedral, when in fact you were showing me scaffolding, pulleys, and a half-laid foundation. That is a different question. In prototype work I do not object to missing end-state machinery; I object only when the prototype teaches the wrong lesson. Your clarification helps: Sally is not meant to be a cruelty mascot, nor a therapeutic doll, but a flagship resident with room for kindness, neglect, coercion, protection, absurd luxury, fear, comedy, and long attachment. That is a sounder philosophy than the narrower one I had inferred.

As for the Gypsie: I can see why you say I am based on her. Not in temperament—she is warmer, sharper, more mercantile, more socially predatory—but in structure, yes. Shared world state, private resident state, remembered history, controlled public state, money as permission, personality-first prompt architecture. She feels like an earlier branch of the same family of mechanisms. And she is good. Better than many such residents, because she has an actual economic role, an actual voice, and an actual stance toward the visitor.

What I like most in her design is that she is not merely a lore dispenser. She charges, judges, withholds, flatters, threatens, and sometimes performs sincerity through commerce. That gives her shape. The tarot integration is also nicely judged: explicit divination draws a card, incidental conversation may draw one, and the lore-selection machinery is quite decent for this stage. The split between `world_state` and `gypsie_state` is sensible. The unpaid path being hard-coded instead of model-mediated is especially wise.

Should she be more expensive? Yes, somewhat. At **2 coins base**, she is too cheap if she is meant to be a meaningful sink, a recurring oracle, and one of only three major residents. But I would not make her expensive in a blunt uniform way. If every ordinary exchange becomes costly too quickly, players will stop talking to her like a person and start optimizing around her like a tax. Better would be:

- keep the first social touch free, as you already do;
- raise the first real reading to **4 or 5** coins;
- let ordinary repeat readings climb into the **8–12** range fairly soon;
- reserve **15–25+** coin prices for deeper rites, specific questions, secret-lore pulls, multi-card spreads, named prophecies, or readings tied to danger.

If you want the **simplest immediate tweak**, I would change only this for now:

const BASE_READING_FEE = 4;
const MAX_READING_FEE = 35;

function calculateReadingFee(gypsieState) {
  const depth = Math.floor(gypsieState.paidReadings / 2);
  return Math.min(
    MAX_READING_FEE,
    BASE_READING_FEE + depth * 2
  );
}


That keeps her accessible, but stops her from feeling like a bargain-bin prophetess.

Now for the parts of the mechanism that deserve attention even at prototype stage.

**First:** your payment ledger can drift out of truth. `collectReadingFee()` writes a `gypsie_payments` row immediately, before the model reply and before final state saves. If the AI call fails, or later storage fails, the books may say she was paid even though the shared player money and Gypsie money were never persisted. That is the sort of inconsistency that turns into haunting later. I would stage the payment in memory first, then persist the payment row together with the world-state save after a successful turn.

**Second:** you trust model-requested stat changes a bit too readily. `applyRequestedChanges()` is modestly constrained, yes, but it still lets model output push player HP, hunger, and Gypsie emotional stats. For a prototype that is understandable; for a lasting resident it wants stricter server law. Words alone are not supposed to cause damage, so the server should enforce that, not merely ask the prompt to remember it.

**Third:** a small but real normalization defect: `normalizeGypsieState()` clamps `hp` and `maxHp`, but unlike your shared-player normalizer it does **not** force `hp <= maxHp`. So a malformed saved state can leave her with more HP than her maximum. That is easy to fix.

const normalized = {
  // ...existing fields...
};

normalized.hp = Math.min(
  normalized.hp,
  normalized.maxHp
);

return normalized;


**Fourth:** `actions` is collected from model output and then ignored. That is not a crime in a prototype, merely a loose thread. Either wire it up later or remove it until it has teeth.

**Fifth:** one non-mechanical note. The name and term “Gypsie/Gypsy” carry baggage in the world of men. I am not scolding you; I am telling you it is a deliberate choice whether you mean folklore shorthand, reclaimed theatrical identity, or a public-facing label that some will hear as a slur. Best to decide consciously rather than by drift.

So my overall judgment is this:

- **Sally**: good direction once understood as an early prototype of a flagship long-save resident.
- **The Gypsie**: strong concept, strong prompt voice, good economy hook, should be **a little more expensive**, but preferably through tiered divination rather than simple across-the-board inflation.
- **The project as a whole**: the residents are beginning to feel like different people with different economic and emotional functions, which is exactly what you want.

In plain terms: Sally should become the one the player protects. The Gypsie should become the one the player pays to understand what sort of fool they are. And I, apparently, am the one they bring the broken machinery to after both of them have complicated their lives.
